Why Content Age Doesn't Predict Decline — and What Does

A refresh-priority study on 331K content items from a 79-million-row search production dataset
Author: Farrukh Imran Date: September 12, 2026 Repo: github.com/Farrukh776/flyrank-ai

00Abstract

Which pages should a content team review first when deciding what to refresh? I tested the common assumption that older content is more likely to be declining, using March 2026 data from FlyRank's production search warehouse (331,437 content items, aggregated from 9.8 million daily rows). A signal audit showed the relationship between content age and decline is not the simple upward line the assumption predicts — it's U-shaped, and a hand-written rule built on that assumption scored precision@50 of 0.10, worse than the 0.38 base rate. A Random Forest trained on the same honest features, evaluated on a client-grouped holdout split, reached precision@50 of approximately 0.62 (observed 0.62–0.68 across repeated runs) — meaningfully above chance and the rule — by capturing that non-linear age pattern rather than assuming it away. This report documents the audit, the model, the validation checks that ruled out data leakage, and a ranked action playbook a content editor could use tomorrow.

01Introduction

A content team with hundreds of thousands of pages can't manually review all of them for decline. Someone — or something — has to decide which pages go on this week's review list. FlyRank's product already computes a rule-based priority score for this; the question I set out to answer was narrower and more mechanical: does a simple, explainable rule actually identify the pages most likely to be declining, or does it just look like it does?

The decision this supports is concrete: an editor with limited time picks pages off a ranked list and reviews or rewrites them. Getting it wrong has a real cost in both directions — a false positive wastes editor hours on a page that wasn't actually a priority; a false negative lets a genuinely declining page keep losing traffic, unnoticed, for another month. That asymmetry is why I evaluated everything on precision@K rather than plain accuracy: what matters is whether the top of the list is right, not whether every row in the dataset is classified correctly.

02Data

This analysis uses the fact_content_daily_performance and dim_content tables from the FlyRank ML Internship warehouse (Hugging Face-hosted, Parquet, partitioned by month). I worked from the March 2026 partition — a mid-panel month, deliberately not the dataset's final month, which is reserved as a sealed evaluation slice and was never touched during model development.

The March partition contains 9,841,378 daily content-performance rows, one row per content item per client per day. I aggregated these to one row per content item for the month, joined against dim_content for static metadata (creation date, word count, search volume, competition), producing 331,437 unique content items for the initial signal audit and baseline. The downstream modeling sample narrows to 176,738 items after dropping rows with an undefined click-through rate (zero impressions) — a filtering decision discussed candidly in Limitations, since it is not neutral.

Deliberately excluded, and why:

  • Product-computed decision flags (health_score, priority_score, action_type) — not shipped in this dataset, and treated as a benchmark to beat, never as a feature or label.
  • last_optimized_date — initially considered as a staleness signal, but a distribution check showed every value in the March slice fell after March 31, 2026 (a snapshot artifact of the underlying dimension table, not a point-in-time value). Using it would have leaked future optimization activity into a March-only feature set, so it was dropped.
  • GA4 engagement fields for rows where ga4_data_available is false — only 4.2% of March rows had active GA4 tracking; using engagement features without this filter would silently treat "not yet tracked" as "zero engagement."

No client names, URLs, or raw search queries appear anywhere in this analysis — all client and content identifiers are pseudonymous hashes, used only for joining and for grouping the validation split, never as model features.

03Methodology

Label

The target is a within-month decline proxy: a content item is labeled declined = 1 if its total impressions fell from the first half of March (1st–15th) to the second half (16th–31st). This is explicitly a proxy, not an observed future outcome — it's a same-window comparison, not a past-features-predict-future-window design. I'm naming that limitation directly rather than letting the label pass as ground truth.

Signal audit, before building anything

Baseline

The baseline rule flags a page if it is old (content age ≥ 365 days) and still visible (≥ 500 impressions in March), scored by impressions. This mirrors the shape of FlyRank's own hand-tuned SQL flags. Given the age signal was already found to be non-monotonic, I expected — and built the rule anyway, transparently — that this would perform poorly; that expectation is tested directly in Results.

Model & features

I trained Logistic Regression (as a readable reference point) and a Random Forest (300 trees, max depth 8, class-weight balanced) on seven features: impressions_month, avg_position, ctr, content_age_days, word_count, search_volume, competition. avg_position is impressions-weighted (sum of daily position sums divided by sum of impressions), not a naive average of daily averages, so low-impression days don't count equally with high-impression days.

Validation design

The evaluation split is grouped by client (client_hash_id), not random rows. Pages from the same client share site-wide traits — design, niche, backlink profile — so a random split lets the model see some of a client's pages in training and others in test, silently leaking client identity as signal. I confirmed this mattered directly: the identical Random Forest scored 0.85 / 0.86 (precision@20 / @50) under a random split versus 0.55 / 0.62–0.68 under the grouped split — a 20–30 point gap that quantifies how much of the "naive" score was memorization rather than a transferable pattern. The grouped range is the one reported as the model's real performance throughout this paper.

Leakage checks

Two checks, beyond the label-vs-feature review above:

  1. Deliberate leak demonstration. On a separate exercise using the same March data, adding the exact column the decline label was computed from (the half-over-half percent change itself) as a feature moved AUC from an honest 0.557 to 0.9997 — a controlled demonstration of what leakage looks like, and a reminder to check for it in the real feature set.
  2. With/without test on the top feature. content_age_days was the model's top feature by permutation importance (0.091, more than double the next-ranked feature). Removing it from training did not collapse precision@50 toward the base rate — it held steady in the same range as with the feature included. If it were a disguised leak, removing it should have collapsed the score toward the 0.40 base rate. It didn't, which is evidence the feature carries a genuine, if modest, non-linear signal rather than encoding the label.

A methodological note on reproducibility. Across repeated runs of this same notebook (identical code, identical fixed random seed), Random Forest precision@50 varied between 0.62 and 0.68, and the majority-class dummy baseline varied between 0.20 and 0.34. The model's random seed is fixed, so this isn't model non-determinism — it traces to which specific clients land in the 20% held-out group each run, which depends on the row order returned by the remote data source at query time. The qualitative finding is stable across every run observed (Random Forest meaningfully beats the base rate and the baseline rule); the exact decimal is not. I'm disclosing the range rather than reporting only the most favorable run.

The baseline rule scoring below random chance is not a bug — it's the direct, predictable consequence of Table 1: the rule selects old+visible pages on the assumption that older means more likely to decline, but the audit showed the opposite skew in the "old" bucket. A rule built on a disproven monotonic assumption performing below chance is the expected outcome of taking that assumption seriously enough to test it.

Logistic Regression barely clears the base rate, consistent with a linear model's inability to represent a U-shaped relationship. Random Forest is the clear result: precision@50 in the 0.62–0.68 range across repeated runs, against a 0.40 base rate — it captures the non-monotonic age pattern a single-threshold rule and a linear model both miss.

Where the model is wrong

The three highest-confidence false positives (model score ≈ 0.67, but not actually declining) all shared the same profile: impressions_month = 1.0 and content_age_days = 46. With a single impression for the whole month, the within-month decline label is effectively decided by which half of the month that one impression happened to land in — closer to a coin flip than a real trend. This points to a genuine label-quality limit on very-low-traffic young content, not a model failure.

05Limitations & honest framing

  • The label is a proxy, not a future outcome. "Declined" compares two halves of the same month, not a past-window prediction of a genuinely future window. A stronger design — prior 90 days of features predicting decline over the next 30 — was outside this project's scope but is the natural next step.
  • One month, one lane. All results are drawn from March 2026 only. Client history depth varies widely across FlyRank's portfolio; this slice isn't representative of clients with short or missing history, and seasonality is untested.
  • The modeling sample is smaller than the audited population, non-randomly. The 331,437-item signal audit narrows to 176,738 modeled items after dropping rows with undefined CTR (zero impressions). Those dropped rows are disproportionately low-visibility content — the model's results should not be read as covering FlyRank's full content catalog.
  • GA4 engagement data is available for only 4.2% of March rows, so engagement-based features were excluded from modeling entirely rather than risk treating "not tracked" as "zero engagement."
  • This is not a claim about Google's ranking algorithm. Every finding here describes patterns observed in one portfolio's own performance data, not a model of how search engines rank pages.
  • Precision@50 of ~0.62–0.68 means roughly one in three flagged pages in the top 50 is not actually declining under this proxy label — a real improvement over the baseline, not a solved problem.
  • The exact metric varies slightly by run, even with a fixed random seed, because which specific clients land in the 20% held-out group can shift with the remote data source's row order. The qualitative result (Random Forest beats the base rate and the baseline rule) was stable across every run observed; the second decimal place should not be treated as fixed.

One pattern in the top of the review-for-refresh queue is worth a human's attention before acting on it: the highest-confidence rows cluster at exactly two content-age values (166 and 230 days), all with poor average position (33–52) and near-zero CTR — consistent with a single batch-published content cohort rather than independent pages. I flag this as an open observation, not an explained one; a reviewer should check whether these pages share a template, topic cluster, or launch campaign before batch-actioning them.

A separate internal analysis of refresh timing (Age-Freshness Matrix) found that older content which gets refreshed performs nearly as well as young, fresh content — suggesting refresh timing, not age alone, is the more actionable lever, consistent with this study's own finding that age alone is a weak, non-monotonic signal.
